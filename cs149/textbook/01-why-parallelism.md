## 1. 问题从哪里来：处理器越来越多，程序会自动更快吗？

我们先从一个具体而可计时的任务开始：给定 4,000 万个整数，求所有整数之和。串行程序会让一个线程依次读取并相加。增加 CPU 核心后，直觉方案是把数组拆成四段，四个 Worker 各算一个部分和，最后再合并。

计算本身可以并行，但要让结果正确，你必须解决另外三个问题：

- **划分**：不同 Worker 是否处理了互不重叠、又覆盖完整输入的工作？
- **协调**：部分和什么时候可读？最终谁负责合并？
- **成本**：创建任务、读取内存、写入结果和等待同步是否划算？

这正是并行程序与普通顺序程序的不同。任务可以被拆分，**不意味着拆分是免费的**。

### 课堂案例：人群扮演处理器

官方课件开头有若干现场加法实验。视频概要记录了约 [05:07](https://www.youtube.com/watch?v=V1tINV2-9p4&t=307s) 开始的计算活动、约 [09:30](https://www.youtube.com/watch?v=V1tINV2-9p4&t=570s) 对通信问题的讨论和约 [14:49](https://www.youtube.com/watch?v=V1tINV2-9p4&t=889s) 多人分工的负载不均情形。

把参与者当作 Worker：每个人局部加法很快，但只要彼此传递结果的时间太长，加入第二个人也不一定明显加速。再加入更多人，任务难易不一时，有些人先完成并空闲，最终耗时仍由最慢的路径决定。

这个案例同时引出了两类最重要的并行瓶颈：

**Communication overhead**：并行单元需要交换结果或等待数据，导致不能持续计算。

**Load imbalance**：任务分配不均，部分单元提前空闲，导致最后一个 Worker 决定完工时间。

后面的 L5、L6 会进一步分析这两种现象，并讲解 Work Stealing、Locality、Contention 等优化机制。

## 2. 什么是 Speedup？什么时候“更快”不等于“高效”？

对于**同一个问题、同样的输出要求**，定义：

```text
Speedup(P) = T(1) / T(P)
Efficiency(P) = Speedup(P) / P
```

这里 T(1) 是 1 个处理单元执行的时间，T(P) 是 P 个处理单元执行的时间。Efficiency 是一种对相同类型处理单元的加速效率指标；在异构 CPU/GPU 系统中，单靠除以 P 不能衡量成本与能源效率。

举例：单核耗时 100 ms；8 核耗时 20 ms。

```text
Speedup(8) = 100 / 20 = 5x
Efficiency(8) = 5 / 8 = 62.5%
```

它确实快了 5 倍，却没有达到理想的 8 倍。损失的部分可能来自任务调度、通信、串行收尾、Cache / Memory 资源争用等。

对业务而言，5 倍提速可能极有价值。对系统设计而言，你仍须解释 **为什么剩余 37.5% 的理论并行能力没有转化为收益**。

### 不能比较什么？

如果单核版本运行的是排序完整数据、并行版本只排序了其中一半，计算结果不同，Speedup 就没有可比性。若单核版本用差算法、并行版本换了复杂度更优的算法，获得的提升也不能全部归因于并行硬件。

做性能工程时，要同时报告：

- 输入规模、数据类型、正确性要求；
- 基线算法、编译选项、硬件与内存布局；
- 测试次数与统计口径；
- 是否包含数据准备、分配、传输和同步。

## 3. 为什么“只提高主频”不再可靠？

理解现代 GPU，先要看 CPU 曾依赖的两条道路：**提高时钟频率**和**在单线程里自动发掘独立指令**。

一个 CPU 的指令可以抽象成“取指 → 解码 → 读取寄存器 → 运算 → 写回状态”。真实处理器复杂得多，但这有助于理解：程序虽然按顺序写成，部分指令在数据上可能互不依赖。

考虑表达式：

```cpp
int a = x * x + y * y + z * z;
```

可以把它拆成五项操作：

```text
  x*x ----\
           + ----\
  y*y ----/       + ---> a
  z*z ------------/
```

三个乘法彼此独立，理论上可以由多个执行单元同时执行；而最后的加法依赖前面的结果。

这叫 **Instruction-Level Parallelism（ILP）**。Superscalar / Out-of-Order CPU 试图动态找出可并行执行的指令。但 ILP 受到指令依赖、分支、数据未就绪等因素限制。即使 CPU 配置更多运算单元，程序不一定存在更多**可同时执行的独立指令**。

官方 Slides pp. 38–51 通过依赖图与 Superscalar 处理器逐渐推导这一约束。

### 另一个硬约束：Power Wall

动态功耗可用近似关系描述：

```text
P_dynamic ∝ C * V² * f
```

C 是有效开关电容，V 是供电电压，f 是时钟频率。提高频率往往需要改变电压，因此功耗与热设计成本可能增长得很快。此外，晶体管在没有执行有用计算时也会有静态漏电功耗。

这不是说 CPU 主频不可能继续提高，而是**持续依赖升频获得过去那种指数式性能增长，已经不现实**。更具经济性的路径是使用多核、向量单元、GPU 或专用加速器，去运行能够并行化的程序。

官方 Slides pp. 52–66 从功耗约束转到多核 CPU、GPU、移动 SoC 及 TPU/NPU 等实例。

## 4. 从 CPU 到 GPU：为何“专用”计算能力越来越重要？

想象两种处理器设计：

- 设计 A：非常擅长不规则分支、复杂控制逻辑和单个任务的低延迟响应。
- 设计 B：简化单个执行单元，把更多芯片资源投入大量重复、相似的运算。

A 很像通用 CPU 的设计取向，B 很像高吞吐量 GPU 的设计取向。两者不是绝对二选一，而是不同负载下的资源分配权衡。

例如，大矩阵乘法包含大量重复乘加操作、规则数据访问和可并行处理的块。GPU 的大量执行单元适合这种工作；但一个读取单条请求、复杂解析与分支逻辑密集的控制任务，不一定天然适合 GPU。

AI 工作负载正好兼具这两种需求：

- **Control plane**：任务提交、数据准备、调度、失败恢复、指标收集，通常更适合 CPU / 分布式服务。
- **Data plane**：矩阵乘法、卷积、Attention Kernel，以及高吞吐度训练计算，通常希望在 GPU / 专用加速器上执行。

把 LLM 部署到 GPU 上不代表整条请求路径都应该搬进 GPU。系统设计的重点是：**给不同工作选合适的计算资源，再控制跨资源的数据传输和调度开销。**

## 5. 为什么数据移动比想象中重要？

一条加法指令可能很便宜，但如果它需要的数据不在寄存器或近端 Cache，CPU 可能必须等待更慢的内存层级。

课件后段用一个具体 CPU 架构举例展示 L1/L2/L3/DRAM 的访问延迟差异（Slides p.80），说明不同数据位置的读取代价可能相差许多倍。数字属于特定处理器和测试条件，**不应被当成所有现代 CPU 的固定延迟表**。

对 AI Infra，这个思想可以扩展到另一组数据路径：

```text
CPU DRAM  <-->  PCIe / NVLink  <-->  GPU HBM
                                         |
                                  Shared Memory / Registers
```

当算子不断重复把同样的中间结果写到 HBM、下个 Kernel 又重新读取时，即使算术单元非常强，也可能因为数据搬运而表现不佳。这是后面学习 Tiling、Fusion 和 FlashAttention 的重要前置直觉。

**注意：** 本节的多 GPU、HBM、FlashAttention 连接是现代工程扩展，而不是声称教授在 L1 中已经完整讲解这些实现。

## 6. 可以立即验证的小练习

### 练习 A：有多少加速比？

某程序单线程 80 ms，4 线程 28 ms，8 线程 19 ms。

求：

1. 4 线程和 8 线程各自的 Speedup；
2. 两个版本的 Efficiency；
3. 是不是所有工作都已经并行？
4. 为什么不应只看“8 线程版更快”这一个结论？

**参考解答：**

```text
S(4) = 80/28 ≈ 2.86x, E(4) ≈ 71.4%
S(8) = 80/19 ≈ 4.21x, E(8) ≈ 52.6%
```

8 线程绝对时间更短，但单位处理单元的扩展效率更低。是否存在串行段、内存带宽上限或其他瓶颈，需要继续测试，单凭这三个数字无法确定原因。

### 练习 B：画自己的 Dependency Graph

给定：

```cpp
int a = x * y;
int b = y + z;
int c = a + b;
int d = a * z;
int result = c + d;
```

假设每个运算占一个时间单位、无限多执行单元且忽略调度成本：

- Work = 5 个操作；
- Critical Path 至少 3 步（如 a→c→result）；
- 最大理论并行度的上界为 Work / Span = 5/3 ≈ 1.67（按这个简单模型）。

这提示我们：**独立指令数量**与**总操作数量**不同。后续 Work / Span 模型会更严谨地说明这个边界。

### 练习 C：思考题

假设 GPU Kernel 的计算只有 20 μs，而 CPU↔GPU 的两次传输合计需要 200 μs。你优化 Kernel 到 10 μs，端到端到底加速多少？

**参考解答：**

```text
Baseline: 200 + 20 = 220 μs
Optimized: 200 + 10 = 210 μs
End-to-end speedup = 220/210 ≈ 1.048x
```

Kernel 加速 2 倍，系统整体却只提升约 4.8%。此时应该考虑减少 Host↔Device 传输、让数据驻留设备端，或合并更多有意义的计算。

## 7. 本章重要结论

并行计算的目标不只是“让更多处理器工作”，而是缩短正确任务的完成时间，并以合理的硬件、功耗、通信和工程成本完成它。

本章的核心因果链是：

```text
单线程自动提速变慢
    ↓ 主频功耗受限 + 可挖掘 ILP 有限
采用更多/专用执行资源
    ↓ 需要人为识别可并行的工作
工作划分 + 分配 + 同步 + 通信
    ↓ 不规则工作和昂贵数据移动带来新瓶颈
性能优化 = 正确建模 + 测量 + 解释
```

对于准备 AI Infra 的工程师，这条链比具体记住某代 GPU 的核心数量更重要。
