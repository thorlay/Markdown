## 1. 什么是并行计算？本课程到底教什么？

课程的起点是：多种处理单元协作，以更快地解决一个问题。然而教授同时强调，目标有两个：**performance（性能）** 和 **efficiency（效率）**。

这是关键区别。假设一个程序在一台十核机器上比单核快了两倍：

- 从用户的角度：等待时间减半，可能非常有价值。
- 从资源的角度：如果十个核心同时被占用，仅得到两倍加速，扩展效率并不理想。
- 从硬件设计的角度：也许根本不需要那样多的执行资源，或者应该把芯片面积投入更合适的结构。

教授在开头询问学生为什么选课，得到的回答来自不同方向：硬件架构、图形、机器学习，以及想理解软硬件接口的工程师。课堂随后反复回到一个判断：**知道一项计算“大概应有多快”，是性能工程师的重要能力。**

具体工作可以拆成三个相互依赖的过程：

1. **Decomposition**：把任务分解成能够安全并行执行的子任务。
2. **Scheduling / Work Assignment**：把子任务分配给执行单元，并尽量避免有的单元长时间空闲。
3. **Communication / Synchronization**：让执行单元交换信息、协调依赖，同时控制开销。

你会发现这不仅是线程编程的基本问题，也是并行数据库、分布式训练和 GPU 调度系统的问题。

## 2. 课堂实验：把人当作处理器

教授没有先解释复杂的 CPU 结构，而是邀请学生当场做加法，让“并行”和“通信成本”变成可以观察的事实。

这里需要保留两个前提。第一，参与者加法速度不同，纸片数字的难度也不同。第二，每组使用的不是完全相同的输入，因而这些时间**不能当作严格的、可复现的硬件 Benchmark**。它们的作用是引出系统瓶颈。

### 2.1 实验一：一个人计算 16 个数字

一个学生独立求 16 个纸片数字之和。课堂给出的口头基线是 **大约 40 秒**；随后教授讨论时也提到，如果计入准备纸片等因素，实际可以按约 45 秒看待。

单人版本容易理解：没有跨人的通信，也不存在工作分配和最终归约的问题。所有加法都在同一个人的处理路径里完成。

这并不意味着串行算法最优，只是说它的控制成本很低。

### 2.2 两个人：计算更少，为什么还是约 41.7 秒？

第二次尝试让两个人各自拿到 8 个数字。一人在教室前面，另一人在后面，教授不允许两人直接交谈；但他们可以用纸片等方式传递结果。最终总和需要由两边的局部和汇总得到。

**观察：** 两人完成整项任务大约需要 **41.7 秒**。虽然每个人只计算约一半的数字，但整体时间与单人版本几乎相同。

可把任务划成三个阶段：

~~~text
前方学生：  8 个数字 ──> 局部和 A ──┐
                                    ├──> 汇总 A + B ──> 正确答案
后方学生：  8 个数字 ──> 局部和 B ──┘
                      ↑                ↑
                   可并行计算       需要通信与合并
~~~

如果局部计算在理想情况下各占 20 秒，但“把局部和从教室后面送过来”需要很久，则：

```math
T_{\text{parallel}} \approx \max(T_A,T_B) + T_{\text{communicate}} + T_{\text{combine}}
```

只减少局部计算时间，却没有控制通信开销，整体不一定加速。

**教授进一步讨论的优化**包括：让两人靠近、允许喊出结果、使用即时消息，或者让一人在仍然计算时朝对方走去。这里最有趣的思想是：

> 在有条件的情况下，**将通信与计算重叠（overlap）**，而不是机械地先算完、再开始全部通信。

我们用原创小例子把它转化为时间线：

~~~text
版本 A（没有 overlap）
局部计算  [====================]  20 s
传递结果                      [==========] 10 s
合并结果                                  [==] 2 s
总计：32 s

版本 B（允许部分 overlap，假设依赖允许）
局部计算  [====================]  20 s
通信                  [==========]         10 s
合并结果                                  [==] 2 s
总计：约 22 s
~~~

注意，这个时间线中的 20/10/2 秒是**教学示意**，不是现场实验的原始分项计时。

### 2.3 四个人：更多处理器带来了新的问题

教授接着尝试四人并行。第一版中，四个人得到的任务并不均衡：有人拿到更多或更难的数字，其他人已经完成了计算，只能等待最慢的人。

这叫 **Load Imbalance（负载不均）**。

假设四个 Worker 的计算时间分别是：

| Worker | 局部计算时间（示例） |
| --- | ---: |
| A | 4 s |
| B | 5 s |
| C | 6 s |
| D | 16 s |

如果必须等所有人完成才能做最终合并，局部阶段至少需要 16 秒，而不是平均的 7.75 秒。其他三个 Worker 的空闲并不会让 D 自动更快。

于是课堂讨论了几种不同的策略：

- **Static Partitioning（静态分配）**：事先尽量平均分配数字；
- **Shared Work Pool（共享任务池）**：把未处理的数字放在一起，谁空闲谁领取；
- **Dedicated Reducer（专人归约）**：让一个人负责持续收集并合并其他人的局部结果；
- **Tree Reduction（树形归约）**：部分结果两两合并，避免所有合并都堆到最后一个人身上。

四人再次尝试时，采用了类似共享任务池的方案。课堂观察到：

- **约 12 秒**时，成员已经完成各自的数字计算；
- 后续合并局部结果又花了**约 7 秒**；
- 从开始到报出结果，约 **19 秒**。

因此：

```math
T_{\text{total}} \approx 12s + 7s = 19s
```

这一实验对性能分析非常重要：当计算阶段已经接近理想情况，继续优化每个人的局部加法，可能不如优化最终的归约阶段。

**一个容易被摘要遗漏的细节：四人报出的答案并不正确。** 教授指出学生给出的结果是 125，正确值应为 115，差了 10。19 秒是课堂中“完成并报出”的观察时间，**不是完成正确计算的严格加速记录**。

这还教会我们性能工程的另一个前提：

**Correctness first.** 一个加速十倍、但返回错误结果的实现不是成功优化。

### 2.4 动态调度是不是总比静态调度好？

不一定。共享任务池能缓解 Work Imbalance，但它会引入领取任务、共享数据结构、可能相互干扰等开销。

- 任务大小相近、成本可预测：静态分配可能简单且高效。
- 任务耗时差异大：动态分配可能提升整体利用率。
- 任务非常细碎：每次领取工作产生的开销可能比运算本身还大。
- 局部数据复用很重要：频繁偷取工作可能破坏 Locality。

**重点不在“使用哪一个框架”，而在任务分布、依赖与通信成本共同决定最佳策略。** CS149 的后续章节会继续展开 Work Distribution、Work Stealing 和 Locality。

### 2.5 实验三：整个教室一起统计人数

最后教授提出一个“巨型并行”问题：用在场的同学尽快统计教室里共有多少人。

课堂讨论出现了多种算法：按行计数、按区域聚合、把人分成固定人数的小组，或让人员移动到空行以便统计。

学生最终尝试了需要较大规模**人员移动**的方案。结果在超过两分钟后，教授暂停演示并带大家复盘：

- 为了让人移动到正确的位置，必须不断协调；
- 前排、后排的人没有始终保持有效工作；
- 统计本身很简单，移动人员与同步状态却很贵；
- 更多参与者，不代表更多有效工作。

这里的计算对象几乎变成了系统的“数据”。当算法要求大量搬动这些数据时，协调和移动成本吞噬了并行带来的潜在收益。

教授借此强调了整门课程的一个基调：**在并行系统中，如何把数据放到正确的位置，可能比执行一次计算更重要。**

### 2.6 三个 Demo 的核心知识

| 实验 | 主要观察 | 对应的系统问题 |
| --- | --- | --- |
| 一人 vs 两人 | 计算量被分成两半，但汇总通信成本很高 | Communication |
| 四人分工 | 长尾 Worker、任务领取与最终合并 | Scheduling / Load Balancing / Reduction |
| 全教室统计 | 大量协调、同步与移动，超过实际计算成本 | Data Movement / Synchronization |

## 3. 用数学语言重新描述并行性能

课堂的直觉可以先由几个简洁指标表达。

### 3.1 Speedup（加速比）

对于同一个问题、同样的正确性要求：

```math
S(P)=\frac{T(1)}{T(P)}
```

其中 T(1) 是用一个处理单元的执行时间，T(P) 是使用 P 个处理单元的时间。

例如：

~~~text
单核时间 100 ms
四核时间  30 ms
S(4) = 100 / 30 = 3.33x
~~~

如果只测量 Kernel 却拿它与包含文件 I/O、设备传输的旧版本比，那么两个 T 的边界不同，计算出来的数字没有可解释的意义。

### 3.2 Parallel Efficiency（并行效率）

当 P 个处理单元足够同质、并使用一致的比较方式时，可以定义：

```math
E(P)=\frac{S(P)}{P}
```

四核加速 3.33 倍：

```math
E(4)=3.33/4\approx83.3\%
```

效率并不是直接测量处理器实际“忙碌时间”的指标；它是相对于理想线性扩展的一种简化度量。对异构 CPU+GPU 系统，单纯除以 P 通常不合适。

### 3.3 为何 10 核加速 2 倍，不一定失败？

教授问了一个很有现实意义的问题：如果你使用 10 核，把某应用从 15 FPS 优化到 30 FPS，算不算成功？

从资源扩展看：

```math
S(10)=2,\qquad E(10)=20\%
```

这个效率不高。但如果 15 FPS 无法满足产品要求、30 FPS 已经让产品可用，那么这项优化可能创造了巨大价值。

同样，如果网站响应时间减半能够显著改善体验，或者用户愿意为更低延迟付费，产品可能乐于接受这项硬件成本。

**所以性能优化有两个问题：**

1. 我们能否让任务更快？
2. 以什么计算、能耗、硬件和运营成本换取这份速度？

这里的 Efficiency 不仅是算法层面的效率，也会延伸到单位吞吐量成本、每请求 GPU 秒数、每 token 能耗等工程指标。

### 3.4 一个最有用的粗略耗时模型

对“每个 Worker 独立处理一份任务，最后再合并”的并行算法，可以先写：

```math
T_P \approx T_{\text{setup}} + \max_i T_{\text{work},i} + T_{\text{communication}} + T_{\text{reduction}}
```

这个模型的关键是 **max 而不是 average**。只要最终结果依赖全部工作完成，长尾 Worker 就可能决定总体时间。

但这是帮助思考的近似式。通信与计算可以重叠，Setup 和 Reduction 也可能形成流水线，不能把所有系统机械地等同于这四项的简单求和。

### 3.5 补充推导：Amdahl's Law（本节是课外扩展）

本讲主要让人从实验中感受到串行瓶颈；我们可以再用经典模型形式化：

设原始运行时间中比例 s 的工作不能并行，剩余 1-s 在 P 个处理单元上理想均分。把单处理器时间归一化为 1：

```math
T(P)=s+\frac{1-s}{P}
```

于是加速比为：

```math
S(P)=\frac{1}{s+\frac{1-s}{P}}
```

若 s=0.1、P=16：

```math
S(16)=\frac{1}{0.1+0.9/16}=6.4
```

即便有 16 个理想计算单元，仍只能加速 6.4 倍。实际通信、调度和争用可能进一步降低收益。

**不要把这一推导误认为 Lecture 1 中逐步讲授的全部内容。** 它是为了把课堂直觉连接到常用的系统性能模型。

## 4. 为什么这门课反复强调硬件与软件的接口？

## 5. 一个历史问题：为什么过去“等下一代 CPU”就能提速？

教授接下来回顾了 CPU 性能增长的历史。曾经，对于不少串行程序，即使开发者不改代码，下一代 CPU 也可能明显更快。

课程重点指出两条曾经非常有效的道路：

1. 让处理器从单条指令流中自动发现更多可以并行执行的工作，即 **Instruction-Level Parallelism（ILP）**；
2. 提高处理器的 **Clock Frequency（时钟频率）**。

理解两条道路各自的极限，就能解释为什么现代计算越来越依赖多核、GPU 与专用加速器。

但在讨论现代 CPU 之前，我们先要准确回答一个看似基础的问题：**程序和处理器到底是什么？**

## 6. 从处理器的角度看，一个程序是什么？

高级语言可以有循环、变量、函数和对象；但在处理器执行层面，程序最终体现为可执行指令及其相关状态。

考虑一个简单 C 程序：

~~~c
#include <stdio.h>

int main(void) {
    int x = 1;
    for (int i = 0; i < 10; ++i) {
        x = x + x;
    }
    printf("%d\n", x);
    return 0;
}
~~~

从语义上看，它输出 1024。但 CPU 并不直接理解 C 语法中的循环关键字。编译器会把程序转成目标架构可以执行的指令序列；真实编译器也可能将简单循环直接优化成常量，不保证生成十次独立加法指令。

为了理解概念，教授将处理器简化成三个部分：

~~~text
                 ┌────────────────────┐
                 │  Fetch / Decode    │
                 │   下一步执行什么？   │
                 └─────────┬──────────┘
                           │
                           ▼
            ┌──────────────────────────┐
            │     Execution Unit       │
            │       ALU / 运算单元      │
            └──────────────┬───────────┘
                           │ 更新
                           ▼
            ┌──────────────────────────┐
            │    Execution Context     │
            │  Registers / 程序状态     │
            └──────────────────────────┘
                           ▲
                           │ Load / Store
                           ▼
                  Memory（存储器）
~~~

这是帮助思考的抽象图，不代表真实处理器所有内部模块。

### 6.1 指令的意义：对状态执行操作

示例（自定义伪指令，并非某种真实 ISA 的固定语法）：

~~~text
ADD R0, R0, R1
~~~

设执行前：

~~~text
R0 = 32
R1 = 64
~~~

指令将 R0 修改为 96，R1 保持 64。它可以理解为：

~~~text
1. 获取下一条要执行的指令；
2. 从程序状态中读取输入；
3. 执行运算；
4. 更新程序状态；
5. 继续执行后续指令。
~~~

这一抽象很有价值，因为并行执行必须满足一个硬约束：**最终可观察结果应符合程序要求的语义**。不能为了同时执行指令而随意破坏依赖或程序状态。

### 6.2 哪些工作可以自动并行？

考虑：

```math
a=x^2+y^2+z^2
```

一种简化指令序列是：

~~~text
1. M1 = x * x
2. M2 = y * y
3. M3 = z * z
4. A1 = M1 + M2
5. a  = A1 + M3
~~~

这里共有 5 个算术操作，但它们不是一条必须严格串行的链。

~~~mermaid
flowchart TD
    M1["M1: x × x"] --> A1["A1: M1 + M2"]
    M2["M2: y × y"] --> A1
    M3["M3: z × z"] --> A2["A2: A1 + M3"]
    A1 --> A2
~~~

前三个乘法彼此独立，可以并行执行。第四个操作依赖第一个和第二个乘法；第五个操作依赖第四个加法和第三个乘法。

### 6.3 为什么两组和三组执行单元都只需要三个步骤？

为了简化，先**假设每个算术操作都只占一个相同的时间单位**，没有 Pipeline、资源竞争或其他延迟。

| 时间步 | 一条串行执行流 | 最多 2 个执行单元 | 最多 3 个执行单元 |
| --- | --- | --- | --- |
| 1 | M1 | M1、M2 | M1、M2、M3 |
| 2 | M2 | M3、A1 | A1 |
| 3 | M3 | A2 | A2 |
| 4 | A1 | — | — |
| 5 | A2 | — | — |

原本 5 步的工作，现在最多只需要 3 步；使用三个执行单元时也无法再减少到 2 步，因为存在 **M1 → A1 → A2** 这样的三节点依赖链。

所以：

```math
\text{Ideal speedup} = \frac{5}{3} \approx 1.67
```

即使在这一瞬间可以并行的乘法最多有 3 个，这个依赖图的**平均可用并行度**也不是 3，而是工作总量 5 除以关键路径长度 3，约 1.67。

这里有两个容易混淆的概念：

- **某一步的最大独立操作数量**：在这个例子里，第一步有 3 个乘法；
- **Work / Critical Path（工作总量 / 关键路径）**：决定此简化模型的理论平均并行度上限。

真实 CPU 中，乘法和加法未必具有相同延迟，也可能被 Pipeline 重叠执行，因此 3 个“抽象时间步”**不是对现代 CPU 实际时钟周期的保证**。

### 6.4 Superscalar 与 Out-of-Order Execution

**Superscalar** 指处理器能够在一个周期内发射或执行多个指令（具体程度受设计和资源约束）。**Out-of-Order Execution** 指硬件能够在遵守数据依赖和可观察语义的前提下，将某些就绪指令提前执行。

用刚才的例子：

- 程序员按照先 M1、M2、M3，后 A1、A2 的顺序写代码；
- 硬件识别 M1、M2、M3 相互独立；
- 允许这些乘法利用多个执行单元同时推进；
- 但 A1 不能在 M1、M2 的结果准备好之前使用它们。

这和创建三个 OS 线程、把任务交给三个 CPU 核心**不是一回事**。这里讨论的是**一个指令流内部**由处理器发掘的并行性。

教授用这些案例引出一个核心限制：串行程序本身能自动提取的独立指令往往有限。增加执行单元到一定程度后，瓶颈不再是缺少执行资源，而是**没有足够独立、已就绪的指令供它们使用**。

## 7. 为什么 CPU 不能无限升频：Power Wall

当自动挖掘 ILP 的收益越来越有限时，还能依靠提高时钟频率让原程序更快。但提升频率本身有电路、功耗和散热成本。

简化的动态功耗模型是：

```math
P_{\text{dynamic}}\propto C_{\text{switch}} V^2 f
```

这里：

- **C**：有效开关电容；
- **V**：电压；
- **f**：时钟频率。

如果其他因素相同、保持电压不变，动态功耗随频率近似**线性**增长。但实际芯片提高稳定运行频率时可能需要提高电压；由于电压出现在平方项中，功耗可能增长得明显更快。

举个数学例子（纯模型，不是 CPU 实测）：

~~~text
原始频率 f，电压 V
频率提高 20%，电压保持不变：
动态功耗约 1.20x

频率提高 20%，电压也提高 10%：
动态功耗约 1.20 × 1.10² = 1.452x
~~~

此外还有静态漏电功耗、温度、散热设计与散热能力边界。课程里教授使用“功耗大致随频率平方增长”作为直觉规则，但**不能把它当作固定电压下的普适物理定律**；更严格的近似模型是上面的 C·V²·f。

两个历史原因共同推动多核、GPU 和专用加速器成为主角：

1. 单一指令流可自动提取的并行度存在上限；
2. 靠持续提高时钟频率获取更高单线程性能，会遭遇功耗和热设计约束。

于是如果软件希望使用新增的大量执行资源，就必须显式表达更大规模的并行工作。

**对应 Slides：PDF pp. 49–55。**

## 8. 多核 CPU、GPU 与专用加速器：如何选择硬件形态？

处理器设计者可以把更多晶体管资源投入不同方向：

- **更复杂的单核**：提高分支预测、执行和缓存能力，以改善单线程延迟；
- **多个通用 CPU 核心**：让独立任务和多个线程真正并行；
- **SIMD / GPU**：让大量规则的数据并行计算获得更高吞吐；
- **专用加速器**：对特定操作做硬件定制，以改善单位性能、功耗或芯片面积。

Lecture 1 展示了从多核 CPU、NVIDIA GPU 到 GPU 超算、手机 SoC、Google TPU 等不同例子。它们不是“CPU 被 GPU 取代”，而是不同计算模式对性能与成本的要求不同。

这里必须保留一条工程直觉：**某台机器拥有多少 FLOPs，不等于一段程序就能获得多少 FLOP/s。** 如果程序没有足够独立的工作，或数据无法及时送到计算单元，峰值算力可能远远用不上。

课程中的具体 CPU/GPU 规模与规格是 2023 年当时的教学示例；对当前硬件选型，应另查最新版产品规格。

## 9. 计算为什么会被 Memory Stall 卡住？

课程最后一个技术主题把“数据移动”从抽象讨论落到了存储层级。

### 9.1 从程序角度看：Memory 是地址到值的映射

在最简化的模型中，内存可以看作一组从地址到字节值的映射：

~~~text
Address   Value
0x00      16
0x01      255
0x02      14
0x03      0
...
~~~

程序通过 **Load** 从地址读取值，也可以通过 **Store** 向地址写入值。

这个抽象并没有规定值必须存放在 DDR、DRAM、SRAM、Cache 或某个特定芯片里。硬件负责实现这个可用的地址空间与访问语义。

### 9.2 为什么 Load 可能让后续指令停下？

假设程序执行：

~~~text
LOAD R0, [addrA]
LOAD R1, [addrB]
ADD  R2, R0, R1
~~~

第三条指令必须使用前两条 Load 的结果。若它们需要访问较慢的内存，相关数据还没就绪，依赖的运算就不能正确推进。

这类等待称为 **Stall**。处理器可能利用乱序执行去运行其他独立指令，或借助多线程隐藏部分等待；但这些机制不能保证把所有内存延迟消除。

特别需要记住：

**Memory Latency** 是某次访问需要等待多久；**Memory Bandwidth** 是单位时间内可以传输多少数据。它们相关，但不是同一个量。

### 9.3 Cache 的关键思想：把常用数据放得更近

Cache 是高速、容量相对较小的存储结构，维护主存一部分数据的副本。正常情况下它不应改变程序的正确结果，却会显著影响访问速度。

处理器并不是每次只把一个字节搬进 Cache，而通常按一个 **Cache Line** 粒度搬运一段连续地址的数据。真实的 Line Size 与 Cache 结构因硬件而异。

这产生两种典型局部性：

- **Spatial Locality（空间局部性）**：刚访问一个地址后，邻近地址也很可能被访问；
- **Temporal Locality（时间局部性）**：刚访问一个地址后，短时间内又可能重复访问它。

在性能分析中，Cache 就是在用有限的片上空间，换取“从远处反复搬数据”的成本下降。

## 10. 把官方 Cache 示例逐步算清楚

Slides 中有一个很好的练习：把 16 个字节的数组，放到一个极小的抽象内存模型中。注意，这一完整访问表**在 Slides 中存在，但上传的录课转写在接近结尾处表示将在下一讲继续推演**；因此下面是根据 Slides 补齐的教材推导，而不是声称课堂已经讲完了每一行。

**模型假设：**

- 16 字节主存，地址从 0x0 到 0xF；
- Cache 容量 8 字节；
- 每个 Cache Line 为 4 字节，因而最多容纳 2 行；
- 替换策略为 LRU（Least Recently Used）；
- Cache 初始为空，加载整个 Line；
- 为简单起见，假设足够灵活的两行全相联存储，不讨论真实硬件的映射组、写策略等复杂因素。

四条可能的 Line：

| Line 起始地址 | 覆盖的字节地址 |
| --- | --- |
| 0x0 | 0x0、0x1、0x2、0x3 |
| 0x4 | 0x4、0x5、0x6、0x7 |
| 0x8 | 0x8、0x9、0xA、0xB |
| 0xC | 0xC、0xD、0xE、0xF |

### 10.1 示例 A：同一段数据被重复访问

访问顺序：

~~~text
0x0, 0x1, 0x2, 0x3, 0x2, 0x1, 0x4, 0x1
~~~

可以逐步分析：

| 当前访问 | Hit / Miss | 理由 | Cache 中的行 |
| --- | --- | --- | --- |
| 0x0 | Miss | 初次访问，加载 0x0–0x3 | 0x0 |
| 0x1 | Hit | 与 0x0 属于同一 Cache Line | 0x0 |
| 0x2 | Hit | 同一行，空间局部性 | 0x0 |
| 0x3 | Hit | 同一行，空间局部性 | 0x0 |
| 0x2 | Hit | 最近访问过，时间局部性 | 0x0 |
| 0x1 | Hit | 最近访问过，时间局部性 | 0x0 |
| 0x4 | Miss | 加载另一行 0x4–0x7 | 0x0、0x4 |
| 0x1 | Hit | 0x0 行仍然驻留 | 0x0、0x4 |

因此 **8 次访问中有 2 次 Miss、6 次 Hit**。这解释了为什么“顺序访问”和“在较小工作集内反复访问”很容易获得 Cache 收益。

### 10.2 示例 B：工作集超过 Cache 容量

另一组访问遍历 16 字节，然后重新访问 0x0：

~~~text
0x0, 0x1, 0x2, 0x3,
0x4, 0x5, 0x6, 0x7,
0x8, 0x9, 0xA, 0xB,
0xC, 0xD, 0xE, 0xF,
0x0
~~~

只看需要更新 Cache 的关键步骤：

| 访问 | 结果 | Cache 行 |
| --- | --- | --- |
| 0x0 | Cold Miss，加载 0x0 | 0x0 |
| 0x4 | Cold Miss，加载 0x4 | 0x0、0x4 |
| 0x8 | Cold Miss，逐出 LRU 行 0x0 | 0x4、0x8 |
| 0xC | Cold Miss，逐出 LRU 行 0x4 | 0x8、0xC |
| 0x0 | Capacity Miss，逐出 LRU 行 0x8 | 0xC、0x0 |

其余按顺序访问、落在已经加载的同一行内的地址都命中。总计 **17 次访问，5 次 Miss、12 次 Hit**。

最后一次 0x0 为什么没命中？不是地址从来没有访问过，而是因为 Cache 太小，先前装入的行已被逐出。直观上，这就是工作集超过有效缓存容量所带来的问题。

实际 CPU Cache 还涉及 Set Associativity、写回策略、预取、替换近似等因素，不能把上述教学模型直接当作某台 CPU 的精确实现。

### 10.3 用代码亲自验证两个例子

下面是独立编写的 Python Cache Line LRU 模拟器，只模拟**是否命中**，不模拟真实 Cache Timing：

~~~python
from collections import OrderedDict

def simulate(addresses, line_size=4, line_capacity=2):
    cache = OrderedDict()  # oldest -> newest
    hits = misses = 0

    for addr in addresses:
        line = (addr // line_size) * line_size
        if line in cache:
            hits += 1
            cache.move_to_end(line)
        else:
            misses += 1
            if len(cache) == line_capacity:
                cache.popitem(last=False)
            cache[line] = None

    return hits, misses

case_a = [0, 1, 2, 3, 2, 1, 4, 1]
case_b = list(range(16)) + [0]

assert simulate(case_a) == (6, 2)
assert simulate(case_b) == (12, 5)
print("Both cache examples match.")
~~~

将代码保存为 cache_lru.py，在安装有 Python 3 的环境执行 python3 cache_lru.py；预期打印 Both cache examples match.，无需第三方包。

可以修改 line_size、line_capacity 与访问顺序，观察数据布局如何影响理论命中率。

### 10.4 真实 CPU 的访问延迟差距有多大？

官方 Slides 最后给出 **Kaby Lake CPU、4 GHz** 下的一组示意性访问延迟：

| 数据位置 | 大约 CPU 周期数 | 换算时间（4 GHz） |
| --- | ---: | ---: |
| L1 Cache | 4 cycles | 1 ns |
| L2 Cache | 12 cycles | 3 ns |
| L3 Cache | 38 cycles | 9.5 ns |
| DRAM（较理想条件） | 约 248 cycles | 约 62 ns |

换算方法：4 GHz 时每周期约 0.25 ns。不同型号、频率、访问模式与测量条件会给出不同结果；这里是 **2023 Slides 所使用的特定 CPU 示例**，不是最新 CPU 的性能表。

这一比较有助于回答“为什么我要关注数据移动”。如果每次运算都要等待远处 DRAM，提升几个算术单元的计算能力，收益可能非常有限。

## 11. 把 Lecture 1 的思想迁移到 AI Infrastructure（课外延伸）

这里开始是面向现代 AI/ML Systems 的扩展，而**不是** 2023 年教授在 Lecture 1 中逐项讲过的内容。

### 11.1 GPU Kernel 快，不等于模型服务快

假设某个请求路径：

~~~text
CPU 数据准备             4 ms
Host-to-Device Transfer  3 ms
GPU Kernel              10 ms
Device-to-Host Transfer  3 ms
其他调度                 2 ms
----------------------------
End-to-End              22 ms
~~~

你把 Kernel 优化到原来的一半：

~~~text
原始：22 ms
优化：17 ms
端到端加速：22/17 ≈ 1.29x
~~~

Kernel 本身提升了 2 倍，但系统只提升约 29%。这与课堂双人加法“并行计算快、沟通慢”的故事是同一种性能工程思维。

### 11.2 Distributed Training：局部计算与 Collective

在多 GPU 训练中，每台 GPU 可以独立完成一部分计算，但某些算法阶段必须同步梯度、参数或其他中间状态。

这类似课堂“每个人先算局部和，最后做归约”。学习 NCCL、AllReduce、Tensor Parallelism 时，都可以继续追问：

- 哪部分工作完全独立？
- 哪些阶段有跨 GPU 的依赖？
- 能否把通信和可独立进行的计算重叠？
- 算法增大规模时，通信延迟与带宽会如何变化？

### 11.3 Inference Runtime：Work Pool 和动态 Batch

LLM 请求有不同长度、不同生成阶段和不同显存需求。推理系统需要组织一批批请求，尽量让设备持续处理有用工作，同时控制 TTFT、Token 延迟和公平性。

这和四人领取加法任务的演示有直觉相似之处，但实际生产系统会有队列、内存占用、请求生命周期和复杂依赖，**不能照搬课堂算法**。

### 11.4 Memory Hierarchy：从 CPU Cache 到 GPU HBM

GPU 也存在不同的存储层级。对 FlashAttention、矩阵乘法 Tiling、KV Cache 等问题，关键不仅是计算量，而是：

- 数据在哪一层内存？
- 重用能否在更快的存储层级发生？
- 为何大量中间 Tensor 的物化与重读可能拖慢系统？
- 算子是否需要额外 Host↔Device 或 GPU↔GPU 数据传输？

这正是 Lecture 1 给你建立的底层直觉。

## 12. 常见误区：学习后应当主动纠正哪些说法？

**误区 1：“CPU 核心数翻倍，执行时间一定减半。”**  
错。串行依赖、负载不均、通信成本、共享带宽等都会限制加速比。

**误区 2：“动态调度永远比静态调度好。”**  
错。动态领取任务本身也有开销，并可能降低 Cache Locality。

**误区 3：“四人实验 19 秒证明算法正确且加速了 2 倍多。”**  
不准确。现场答案与正确值有偏差，输入和参与者也不是严格一致的 Benchmark 条件。它是教学演示。

**误区 4：“Superscalar 就是多个 CPU Core。”**  
错。Superscalar 是同一指令流利用多个执行单元发掘 ILP；多核则允许多个指令流并行执行。

**误区 5：“CPU 功耗严格正比于频率平方。”**  
错。常见动态功耗近似为 C·V²·f；现实升频若伴随升压，可能出现强于线性的增长。

**误区 6：“Cache 就是 RAM 的另一种叫法。”**  
错。Cache 是硬件为减少部分数据访问成本而维护的较小、较快的存储层级；它不等同于应用程序的全部地址空间。

**误区 7：“本章出现的 Amdahl、GPU Inference 就一定是课堂原话。”**  
错。本文清楚标记了进一步推导和现代 AI Infra 延伸，不能把它们伪装成 Transcript 已经逐字证实的内容。

## 13. 练习与参考答案

建议先遮住答案，独立回答。每个练习都对应一个可验证的理解目标。

### 练习 1：加速比与资源效率

同一个程序在单核运行 200 ms，在 8 核运行 40 ms。计算 Speedup 和 Efficiency。你会如何向产品经理及基础设施负责人分别解释这个结果？

**答案：** Speedup = 200/40 = **5x**；Efficiency = 5/8 = **62.5%**。产品经理可能关注延迟改善；基础设施负责人还会关注机器成本和能耗。二者并不矛盾。

### 练习 2：减少 Reduction 开销

在课堂四人演示的简化模型里，局部计算是 12 秒，最终归约为 7 秒。若保持局部计算不变，将归约优化为 2 秒，整体提速多少？

**答案：** 原来约 19 秒，改后约 14 秒。Speedup ≈ 19/14 = **1.36x**。这个计算是对课堂分项时间的**假设性优化**，不是实际重做实验的结果。

### 练习 3：独立指令与关键路径

对 a = x² + y² + z² 的五个算术操作，假设每个操作耗时一单位、无限执行资源，最短执行时间为什么不是一单位？

**答案：** 三个乘法能独立执行，但后面的第一次加法必须等待两次乘法，最后的加法又依赖前一个结果，因此存在长度为 3 的关键路径。最短是 **3 个抽象时间单位**。

### 练习 4：Cache 逐出问题

使用两行 Cache、每行四字节、LRU 策略。给定地址序列：

~~~text
0x0, 0x1, 0x4, 0x8, 0x0
~~~

共有几次 Hit 和 Miss？

**答案：** 0x0 Miss；0x1 Hit；0x4 Miss；0x8 Miss 并逐出 0x0 行；最后 0x0 再次 Miss。共 **1 Hit、4 Miss**。

### 练习 5：功耗模型

设动态功耗与 C·V²·f 成正比，C 不变。频率提高 20%，电压提高 10%，动态功耗约提高多少？

**答案：** 1.2 × 1.1² = **1.452 倍**，约增加 45.2%。该估计不含静态漏电以及真实系统随温度和工作负载发生的变化。

### 练习 6：什么值得先优化？

某服务花费：GPU Kernel 8 ms、Host↔Device 传输 16 ms、调度 4 ms。你只能选择一项优化：把 Kernel 加速两倍，或把数据传输减半。哪一项更好？

**答案：**
- 原来总计 28 ms；
- Kernel 加速两倍：4+16+4 = **24 ms**；
- 传输减半：8+8+4 = **20 ms**。

在给定假设与边界下，**减少数据传输更有收益**，因为它是更大的端到端成本项。
